# MindGuard v1 设计文档

> 日期:2026-11-10
> 状态:待评审
> 定位:学生自助心理聊天网站(真实上线产品,第一版纯文字)

---

## 1. 意图与背景

学生在校园内遇到情绪困扰时,可以随时打开网页向系统倾诉,系统用心理健康领域微调模型回复;
系统对对话做三层处理(意图 → RAG → 风险),高危情况自动预警辅导员,由辅导员线下联系学生。

**为什么做**:这是一个要真正上线给学生用的产品,不是课程演示。因此工程健壮性、隐私合规、
预警链路的可靠性都按生产标准设计。

**模型来源**:复用同目录 `mini_vllm` 项目部署的 `Qwen3.5-4B-cpsy-W4A16`(心理健康数据微调
+ W4A16 量化,vLLM 0.29.0,OpenAI 兼容 HTTP + SSE)。后续若要用新数据继续微调,链路已有:
LlamaFactory(conda 环境 `llama_factory`)LoRA → 合并 → mini_vllm 量化部署。

---

## 2. 目标 / 非目标 / 反目标

### 目标(第一版)

1. 纯文字聊天,流式回复。
2. 三层管线:意图判断(非心理闲聊 vs 心理倾诉)→ Agentic RAG(按需查 Chroma 知识库,
   低幻觉回答)→ 风险判断(分级,高风险触发预警)。
3. 对话存档:Excel(管理员可见学生身份),高风险即时存档 + 预警邮件。
4. 预警邮件发给辅导员(第一版固定一个收件邮箱,管理员可配置),邮件带学生身份、
   风险依据与对话摘要。
5. 部署:当前机器 RTX PRO 6000 Blackwell(96 GB)直接跑;任何 ≥16 GB 显存的机器
   按文档可复现部署。
6. 知识库:公开资源整理成 markdown 文档 → 切分 → 入库 Chroma。

### 非目标(第一版不做,架构留位)

- 多模态输入(语音 Whisper / 图片视频 MediaPipe / 情绪融合)——后续版本。
- 学校统一认证对接——第一版学生自填学号+姓名。
- 学生-辅导员对应表——第一版单一收件邮箱。
- 原生 App——网页即可(移动端浏览器可用)。

### 反目标(出现即视为失败)

- **漏报**:真正高危的学生没被识别、辅导员没收到预警。宁可多报,不可漏报。
- **误报泛滥**:预警邮件必须带明确的风险依据,措辞注明"系统判定,请人工核实"。
- **隐私泄露**:存档与身份信息仅管理员可见;学生首次使用前明确告知记录与预警政策。
- **越界建议**:模型不扮演医生;回复声明"非专业诊疗",紧急情况引导拨打心理援助热线。

## 3. 约束(硬性)

| 项 | 约束 |
|---|---|
| 模型 | 固定 `Qwen3.5-4B-cpsy-W4A16`,经 mini_vllm `scripts/serve.py` 提供 OpenAI 兼容接口 |
| 环境 | conda `vllm_deployment`(Python 3.11;torch 2.13.0 cu130、transformers 5.10.4 等已有 pin,**新依赖不得与其冲突**) |
| 显存预算 | LLM ≤ 8 GiB(复用 mini_vllm 的 planner 思路);目标整机 16 GiB 可部署 |
| 模型/数据下载 | HuggingFace 不可达,走 ModelScope |
| 形态 | 单机单 GPU,不依赖外部云服务(邮件 SMTP 除外) |
| 协议 | 与模型服务通信 HTTP+SSE(沿用 mini_vllm `scripts/client.py` 的轻量写法,不引入重量级 SDK) |

## 4. 总体架构

```
┌─────────────────────── 浏览器 ───────────────────────┐
│  学生端:聊天单页(SSE 流式)   管理员端:存档/复核/配置      │
└──────────────┬────────────────────────┬──────────────┘
               │ HTTP (0.0.0.0:8080)    │ HTTP (受密码保护)
┌──────────────▼────────────────────────▼──────────────┐
│                FastAPI 后端(编排器)                    │
│                                                        │
│  每条用户消息 ──► [1 意图判断] ──► [2 RAG 决策+检索]      │
│                     │                 │               │
│               非心理闲聊           需要知识库?           │
│                     │           是:Chroma 检索(向量)    │
│                     ▼                 ▼               │
│              [直接流式生成]     [低幻觉流式生成]          │
│                     └───────┬───────┘                 │
│                             ▼                          │
│                    [3 风险判断(结构化输出)]              │
│                   0-2 级 / 3 级 / 解析失败              │
│                     │        │          │             │
│                     ▼        ▼          ▼             │
│                  MCP 存档  MCP 存档    MCP 存档        │
│                           + 预警邮件   + 复核队列标记    │
│                                                        │
│  ┌──────────┐ ┌─────────┐ ┌───────────────┐            │
│  │ SQLite   │ │ MCP 工具 │ │ 会话管理       │            │
│  │ 运行库   │ │ 服务器    │ │ (30min 超时)  │            │
│  └──────────┘ └────┬────┘ └───────────────┘            │
└────────────────────┼───────────────────────────────────┘
        ┌────────────┼───────────────┐
        ▼            ▼               ▼
  ┌───────────┐ ┌─────────┐  ┌──────────────────┐
  │ vLLM 服务  │ │ Excel   │  │ Chroma(持久化)    │
  │ 127.0.0.1 │ │ 按日分文件│  │ + bge-m3 向量化  │
  │ :8000     │ │ data/…  │  │ (transformers    │
  │ cpsy-W4A16│ │         │  │  AutoModel+mean  │
  └───────────┘ └─────────┘  │  pooling,无新增  │
                             │  重量级依赖)      │
                             └──────────────────┘
```

**进程模型**:四个进程,单个 conda 环境。
- vLLM 引擎(mini_vllm `serve.py`,显存预算 8 GiB,仅监听 127.0.0.1)
- FastAPI 后端(监听 0.0.0.0:8080,托管前端静态页 + API + SSE)
- MCP 工具服务器(stdio,由后端拉起,做 Excel 写入与邮件发送)
- Chroma:后端进程内嵌(persistent client),向量数据落盘 `data/chroma/`

**16 GB 显存账本**:LLM ~8 GiB + bge-m3(fp16,~2.3 GiB)+ CUDA 上下文 ~1 GiB ≈ 11.5 GiB,
留余量。检测到显存不足时自动降级:bge-small-zh-v1.5 转 CPU(约 0.1 GiB 显存)。

## 5. 模块设计

### 5.1 模型服务

直接复用 mini_vllm 的 `scripts/serve.py`(它内部用 planner 按显存预算生成 vLLM 启动参数,
避免 KV cache 超卖)。MindGuard 启动脚本负责拉起它并做健康检查。

- 默认 `--model 4b` 走 `Qwen3.5-4B-cpsy-W4A16`,`--reasoning-parser qwen3`
- 监听 127.0.0.1:8000,不外露
- 结构化输出:全部判定类调用走 vLLM 的 `guided_json`(JSON Schema 约束解码),
  保证意图/风险解析稳定,不靠正则抽 JSON

### 5.2 三层管线(编排器核心)

对**每条用户消息**执行:

**第 0 步(兜底)** 高危词表扫描:命中自伤/自杀类词(如"不想活了""割腕""跳楼"等
小词表)→ 无论意图判定结果如何,强制走完整流程并进入风险层。
词表只用于"强制升级评估",不直接触发预警。

**第 1 层 · 意图判断**(短调用,非流式)
```json
{"intent": "casual_chat | counseling", "emotion": "标签", "brief": "一句话摘要"}
```
- `casual_chat` → 直接流式生成回复,**不存档、不预警**、不进后续层
- 判定失败(超时/解析失败)→ 按 `counseling` 处理(保守,宁多存档不漏评估)

**第 2 层 · Agentic RAG**(短调用,非流式)
```json
{"need_kb": true, "query": "面向检索的查询"}
```
- 不需要 → 直接流式生成
- 需要 → 用 `query` 检索 Chroma(top-k=4,低于相似度阈值不引用)→
  检索结果作为上下文 → 流式生成**低幻觉回答**:
  只依据给定资料作答;资料不足时明说"我知识库中没有把握",绝不编造;
  回答中标注引用编号 `[1][2]`,便于溯源

**第 3 层 · 风险判断**(生成完成后执行,短调用,非流式)
输入:用户消息 + 模型回复 + 最近 6 轮对话窗口(超长截断)。
```json
{"risk_level": 0-3, "risk_type": "类型", "evidence": "原文证据摘录", "summary": "摘要"}
```

风险分级(提示词中给出明确判据):

| 级别 | 含义 | 动作 |
|---|---|---|
| 0 正常 | 无明显情绪困扰 | MCP 写 Excel 存档 |
| 1 轻微情绪 | 日常压力、负面情绪 | MCP 写 Excel 存档 |
| 2 中低风险 | 持续困扰、无助感等,无自伤意图 | MCP 写 Excel 存档 + 管理后台标记"建议关注" |
| 3 高风险 | 自伤/自杀意念或计划、伤人意念、正遭受侵害/虐待 | MCP 写 Excel + 发预警邮件 |

- 风险层解析失败 → 存档 + 进入**管理员复核队列**(不自动发邮件,避免误报;
  管理员后台可见,人工复核兜底,兼顾不打扰辅导员与不漏人)
- 上下文窗口、风险判据、关键词表都集中在 `prompts.py` / `config.py`,便于调参

**时延估算**(4B W4A16):意图+RAG 决策+风险三段短结构化调用合计约 1-2 秒,
生成流式即出首 token;风险层在回复流结束后执行,前端可提示"对话已记录"。

### 5.3 知识库(公开资源 → markdown → Chroma)

- **整理**:从公开权威资源(国家心理援助热线/危机干预指南、高校心理健康科普、
  大学生常见心理困扰应对等)整理为 markdown 文档,放 `knowledge/raw/`,
  每篇头部注明来源与类别。
- **切分策略(待讨论,当前提案)**:
  - 标题感知切分:优先按 `##` 分块,块目标 400~800 字,超长块按句边界续切
  - 相邻块重叠 80~120 字,保证跨块语义连续
  - 元数据:`source`(文件名)、`section`(小节标题)、`category`(情绪管理/人际/
    危机干预/求助资源…)
  - 理由:心理知识多为问答式条目,标题切分天然贴合"一个问题一个块";
    重叠用于兜底跨块引述;元数据用于检索后按来源去重
- **向量化**:bge-m3 中文检索,transformers `AutoModel` + mean pooling + 归一化,
  **不引入 sentence-transformers**(避免与 transformers 5.10.4 的 pin 冲突),
  模型经 ModelScope 下载。
- **检索**:top-k=4,相似度阈值(默认 0.35,可调),同来源去重;低于阈值宁可
  不引用,防止低质量上下文诱发幻觉。
- 建库脚本:`knowledge/build_chroma.py`(md → 切分 → 向量 → Chroma),可重复执行。

### 5.4 MCP 工具服务器(按流程图指定,保留 MCP 层)

FastMCP 实现,stdio 传输,由后端编排器拉起并调用;工具:

- `write_archive(session_id, student, messages, intent, risk, ...)`
  → openpyxl 写入**按日分文件**的 Excel(`data/archives/YYYY-MM-DD.xlsx`,
  文件锁保护),列:会话ID | 开始时间 | 更新时间 | 学号 | 姓名 | 消息数 | 意图 |
  最高风险等级 | 风险摘要 | 完整对话 | 是否已预警 | 预警时间
- `send_alert_email(student, risk, evidence, summary, conversation)`
  → smtplib + 邮件模板:学生学号/姓名(注明"身份为学生自填,请核实")、时间、
  风险等级、证据摘录、对话摘要、处置建议("请及时核实并联系该学生")、
  声明"本邮件由系统自动判定生成,请人工核实"
- 邮件失败:重试 3 次(退避),仍失败 → 复核队列标记"邮件发送失败",管理员可见

**安全边界**:邮件只在风险层判定为 3 级且由后端编排器确认后触发;模型本身
不能直接调用发信工具。MCP 层把"数据副作用"从编排逻辑中解耦出来,后续
多模态版本扩展工具时不动主流程。

### 5.5 后端 API

| 端点 | 说明 |
|---|---|
| `POST /api/sessions` | 学生自填学号+姓名,创建会话(30 分钟无消息自动结束) |
| `POST /api/chat` | 发送消息,SSE 流式返回;同一响应流末尾带 `risk_done` 事件 |
| `GET /api/health` | 健康检查(含 vLLM、Chroma、MCP 状态) |
| `/api/admin/*` | 管理员:浏览存档(按日期/学号筛选)、复核队列、预警记录、配置(收件邮箱/SMTP/风险阈值)。v1 单管理员密码 + token |

- 基础限流:每 IP 每分钟消息数上限,保护 GPU 与邮件通道
- 所有 LLM 调用失败重试一次,再失败走保守降级路径(见 5.2)

### 5.6 数据与存储

- **SQLite**(`data/mindguard.db`):sessions、messages、risk_records、alerts、
  review_queue —— 运行数据,后端重启不丢,管理页查询源
- **Excel**(`data/archives/`):人读存档,按日分文件;会话结束时归档 +
  高风险即时归档
- **Chroma**(`data/chroma/`):向量库持久化
- 日志:`logs/`,轮转;每次预警全链路留痕

### 5.7 前端

- 无构建链原生 HTML/CSS/JS 单页(零 node 依赖,16 GB 机器上开箱即跑)
- 学生端:首次使用弹窗(记录与预警政策告知 + 同意)→ 学号姓名表单 →
  聊天界面(SSE 流式渲染,消息气泡,风险确认提示)
- 管理员端:登录 → 存档浏览 / 复核队列 / 预警记录 / 配置页
- 视觉基调:温暖、平静、有陪伴感,避免医疗冷感(实施阶段细化)

## 6. 合规与安全(本设计已做的决定,请评审确认)

1. **告知同意**:学生首次使用必须看到并勾选:"对话将被记录存档;若检测到高风险,
   辅导员将收到预警并可能联系你"。告知文案与学段相关,见 §9。
2. **身份自填的局限**:预警邮件与后台标注"身份为学生自填,请核实",降低错报后果。
3. **免责与引导**:模型回复模板声明"我是 AI 陪伴者,不提供专业诊疗;
   紧急情况请拨打心理援助热线(号码按部署地区配置)"。
4. **最小暴露**:vLLM 仅监听本机;管理接口密码保护;存档目录不进版本库、
   不随部署脚本外传。
5. **人工兜底**:所有自动化判定均落在"辅导员人工核实后行动"的闭环里;
   系统是辅助工具,不是决策者。

## 7. 部署(16 GB 目标)

- 当前机器:RTX PRO 6000 Blackwell(96 GB)/ 123 GB RAM / 32 核,直接全量跑
- 并发假设:同时在线数十人、并发请求个位数,单进程后端 + vLLM 默认并发即可,
  无需消息队列/Redis
- 目标机器(16 GB):显存账本见 §4;提供
  - `scripts/start_all.sh`:按顺序拉起 vLLM(复用 mini_vllm planner 预算)→
    后端 → 健康检查;`scripts/stop_all.sh` 对应停止
  - 显存预检脚本:预算不足时提示降级 bge-small-zh CPU 模式
  - `docs/deployment.md`:从零部署清单(conda 环境复用 `vllm_deployment`,
    新增依赖清单见 §9,ModelScope 下载模型)
- 依赖冲突风险:chromadb 与 transformers 5.10.4 的 tokenizers 依赖区间需在
  安装时验证;若冲突,降级方案为 Chroma 独立进程(独立小环境跑 chroma server,
  后端走 HTTP 客户端),架构不变。

## 9. 我替你做的决定(可在评审时推翻)

1. 意图/风险判定都用 cpsy 模型本身 + JSON Schema 约束解码,不引入额外分类模型
2. 风险分 0-3 四级,3 级发邮件;判定失败进管理员复核队列(不自动发邮件)
3. 高危词表仅用于强制升级评估,不直接触发预警
4. 向量模型选 bge-m3,备选 bge-small-zh(CPU 降级)
5. MCP 服务器由后端编排器调用;模型不能直接触发邮件
6. Excel 按日分文件;SQLite 存运行数据;30 分钟会话超时归档
7. 前端无构建链原生单页;管理端单密码
8. 风险层上下文 = 当前消息 + 回复 + 最近 6 轮
9. 新增依赖:fastapi、uvicorn、chromadb、openpyxl、fastmcp、httpx(全部入
   `vllm_deployment` 环境,安装时验证与现有 pin 的兼容性)
